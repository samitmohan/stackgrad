## 1Introduction
Deep learning frameworks like PyTorch hide the parts worth understanding. You call loss.backward() and gradients appear. You move a model to a GPU and it gets faster, except when it gets slower. You download a chat model and it answers, and the steps between the bytes on disk and the words on screen stay out of sight.
stackgrad rebuilds those parts in plain Python and checks each one against the library it imitates. I started where Andrej Karpathy's micrograd [1] starts, with a single number that computes its own gradient, and took tinygrad's design [2]: a short list of basic operations with known gradients, and everything else composed from them.
The work follows the order a study plan would. Autograd comes first, then a language model trained from scratch, GPUs and kernels, a real pretrained model, a server, fine-tuning, and last the two applications most language-model systems are built for: retrieval-augmented generation, which answers from documents it looks up, and an agent that calls tools. That last step is the goal. A question goes in through an OpenAI-style endpoint, and every number between it and the answer comes from code written here. Each section builds the piece the previous section's result showed was missing, and ends on a measurement.
The framework is 3,350 lines of Python, counting code and docstrings but not blank lines or comments: 1,364 for the engine, 658 for the three backends and their Metal and Triton kernels, 734 for the models, and 594 for the server. The whole repository, with its tests, benchmarks, and this page, is 10,945 (scripts/lines.py).
You do not need to know any machine learning to follow along. Each section explains its idea from scratch before stackgrad implements it. The figures read the project's result files, and several show what the engine on the server returns when you click.


## 2Autograd: how a network learns
A neural network is a function with adjustable numbers inside it. It takes numbers in, pixels or token ids, and returns numbers out. We call the adjustable numbers parameters or weights, and a large language model has billions of them. A new network starts with random weights and gives useless answers. Learning means nudging the weights until the answers get good.
To nudge them in the right direction we need two things. First, a loss: one number that says how wrong the network is on an example, where lower is better. Second, the gradient of the loss with respect to every weight: how much the loss would change if that one weight moved a little. The gradient points uphill, so we step each weight a little the other way. That step is gradient descent, and training repeats it millions of times.
[ASIDE] A network with one weight, trained for one step
Take the smallest possible network,  y=w⋅x, with one weight  w. We want it to output  6 when the input is  2, so we use the squared error as the loss:  L=(wx−6)2. Start from  w=1: the output is  2 and the loss is  (2−6)2=16.
The gradient is  ∂L/∂w=2(wx−6)x=2⋅(−4)⋅2=−16. It is negative, which says that increasing  w lowers the loss. Step against it with a step size (the learning rate) of  0.1:  w←1−0.1⋅(−16)=2.6. Now the output is  5.2 and the loss is  (5.2−6)2=0.64, twenty-five times smaller after one step. [/ASIDE]

With one weight you can work the gradient out by hand. With a billion weights in dozens of layers you need a program that computes them all, and that program is the first part of stackgrad.

### The chain rule as a program
Any computation, however large, is a chain of small steps: multiply, add, take an exponential, and so on. Calculus has a rule for chains. If  z depends on  y and  y depends on  x, then  ∂z/∂x=(∂z/∂y)(∂y/∂x): the effect of  x on  z is its effect on  y times the effect of  y on  z. Automatic differentiation, or autograd, applies that rule to every step of a program.
It works in two passes. The forward pass runs the computation and, as it goes, records every step and which values fed into it, building a graph. The backward pass walks that graph from the loss back to the inputs. It starts with a gradient of 1 at the loss (the loss changes one-for-one with itself) and, at each step, multiplies the gradient arriving from above by that step's local derivative and passes the result down to the step's inputs. A value that feeds into several steps receives the sum of the gradients coming back from each of them. The scheme is reverse-mode differentiation, also known as backpropagation [3], and one backward pass costs about two forward passes for any number of weights.Expressionrelu(x * w + b) ** 2x * x + xlog(exp(a) + exp(b))sigmoid(sum(w * v))

### Nineteen operations with gradients
A tensor in stackgrad, an array of numbers with any number of dimensions, stores a reference to the operation that produced it. An operation is a small class with two methods. forward computes the result from the raw arrays. backward receives the gradient of the result and returns one gradient per input. For multiplication,  z=xy, backward returns  zˉ⋅y for  x and  zˉ⋅x for  y, where  zˉ is the gradient arriving at  z. In general, backward multiplies the incoming gradient by the operation's Jacobian, the table of all its partial derivatives, without building that table: xˉi​=j∑​∂xi​∂yj​​yˉ​j​,where vˉ means ∂v∂L​
For multiplication the whole class is this (stackgrad/mlops.py, without its checks that skip gradients nothing needs):
[CODE]
class Mul(Function):
    def forward(self, x, y):
        self.x, self.y = x, y          # kept for backward
        return x * y

    def backward(self, grad):          # grad is dL/dz for z = x * y
        return grad * self.y, grad * self.x
[/CODE]

Each operation knows only its own inputs. backward() on the loss connects them: it sorts the graph so every tensor comes after the tensors it was computed from, then walks it from the loss back, handing each operation the gradient that has reached its output. Condensed from stackgrad/tensor.py, without the checks that skip tensors needing no gradient (the real one walks the graph with a loop instead of recursion, so a deep graph cannot hit Python's recursion limit):
[CODE]
def backward(self):
    topo, seen = [], set()
    def build(t):                        # every tensor after the tensors it was computed from
        if t not in seen:
            seen.add(t)
            if t._ctx:
                for parent in t._ctx.parents:
                    build(parent)
            topo.append(t)
    build(self)
    self.grad = ones_like(self.data)     # dL/dL = 1
    for t in reversed(topo):             # from the loss back to the inputs
        if t._ctx:
            for parent, g in zip(t._ctx.parents, t._ctx.backward(t.grad)):
                parent.grad = g if parent.grad is None else parent.grad + g
[/CODE]

All of stackgrad's gradients live in one file, mlops.py, in nineteen such operations: add, multiply, reciprocal, exponential, logarithm, sigmoid, power, sum, max, reshape, transpose, broadcast, indexing, concatenation, matrix multiplication, and a few more. Subtraction is adding a negation, and division is multiplying by a reciprocal. Softmax, normalization layers, and the loss are short compositions of the nineteen, and none of them defines a gradient of its own.
Broadcasting needs care. Add a single number to a whole array and NumPy copies the number across the array, and NumPy calls this broadcasting. Each copy receives a gradient in the backward pass, so the backward pass has to add the copies' gradients back into the one original number. stackgrad makes the copy an explicit operation, Expand, whose backward is that sum.

### Checking every gradient two ways
A wrong gradient does not crash anything. The model trains worse instead, and nothing points you to the cause. stackgrad checks its gradients against two independent references. The first is the definition of a derivative: nudge an input up by a tiny amount  h, then down, and measure the slope. ∂x∂f​≈2hf(x+h)−f(x−h)​,h=10−5
The check is slow, since it reruns the function twice per input, but it needs no calculus and no trust. stackgrad compares it with backward's result for 52 operations and layers, and Figure 3 shows a run of all of them on the server.Run gradient checks

The curves still differ by small amounts, because computers store numbers with limited precision. A 64-bit float keeps about 16 significant digits, so each arithmetic step rounds away a little, and two programs that add the same numbers in a different order get different last digits. In 64-bit floats the two frameworks agree at step 1 to 1.8e−15, which is rounding error alone, so the math is identical. Each training step feeds the previous step's tiny differences forward, and the gap grows to 8.4e−4 by the end. In 32-bit floats, which keep about 7 digits and which models use in practice, each rounding step is about half a billion times larger, and the gap reaches 1.3e−2. Switch the figure between the two to compare.
On the laptop's CPU, stackgrad takes 191 ms per training step of this model and PyTorch takes 90.1 ms, so PyTorch runs 2.1 times faster.

### When does an operation run?
Every operation so far ran the moment it was written. stackgrad now waits: c = a @ b records the multiplication and its inputs and returns a tensor that knows its shape and dtype but holds no numbers. The numbers are computed when something reads them, through .numpy(), .item(), printing, .backward(), or .realize(). tinygrad works the same way [2], and so does MLX, the library behind the Apple GPU backend of §6.
[CODE]
c = a @ b      # recorded: c.shape is known, nothing has run
y = layer(x)   # recorded and returned: still nothing has run
y.numpy()      # realize: every operation y depends on runs, inputs first, once each
[/CODE]

Realizing walks the recorded graph from the inputs to the tensor that was read and runs each operation once; an operation nobody reads never runs. For the next operation to be recorded before the last one has run, each of the 20 primitives in mlops.py (the nineteen with gradients and the comparison x < y) states its output's shape and dtype from its inputs', and realize checks every stated shape against the computed one. An input that already holds numbers is captured as it was, so an optimizer step that replaces a weight cannot change a result recorded before it.
Waiting saves nothing by itself. A training step of a 2-layer story model with 128-wide vectors records 178 operations and runs all 178, since every result feeds the loss. On the CPU its losses match eager execution bit for bit, and a step takes 10 ms lazily against 10 ms eagerly. On the Apple GPU two eager runs already differ by up to 4.8e−7, because the GPU sums in a different order from run to run, and lazy and eager runs differ by 4.8e−7; a step takes 4.8 ms against 4.09 ms. Laziness gives a compiler the whole graph before any of it runs, so the compiler can fuse operations into fewer kernels; stackgrad records the graph and stops there (bench/lazy.py, tests/lazy.py).


## 3Turning text into numbers
A network computes on numbers, so before a language model can read anything, text has to become a sequence of integers. A tokenizer does this. It cuts text into tokens from a fixed list, the vocabulary, and replaces each token with its position in that list.
Single characters make a tiny vocabulary, but sentences become long sequences, and the model must learn to spell before it can learn anything else. Whole words make sequences short, but the vocabulary explodes, and the model has no way to represent a word missing from it, such as a name or a typo. Modern models use subwords. Common words get one token each, and rare words get a few.
stackgrad's tokenizer uses byte-level byte-pair encoding [4] [5], the scheme behind GPT-2, GPT-4, and Qwen. It starts from bytes. Text in any language, emoji included, is a sequence of UTF-8 bytes, and only 256 different bytes exist, so no input is unknown. Then it learns merges. It finds the pair of adjacent symbols that occurs most often in the training text, adds that pair to the vocabulary as a new symbol, and repeats until the vocabulary reaches the size you asked for.
[ASIDE] Four merges on a tiny corpus
Suppose the training text contains low 5 times, lower 2 times, newest 6 times, and widest 3 times. Count every adjacent pair of letters, weighting each word by how often it appears. The pairs e s and s t both occur 9 times (6 in newest, 3 in widest), more than any other, so the first merge creates the symbol es. Recount, and es t now leads with 9, so the second merge creates est. Then l o and lo w lead with 7 each. After four merges, low is a single token and newest is n e w est. [/ASIDE]

Encoding new text replays the merges in training order. stackgrad adds two refinements. First, a regular expression cuts the text into words, numbers, and punctuation before any merging, so a merge never spans two words, and dog in "dog." and "dog!" becomes the same token. Second, for speed, stackgrad counts word frequencies in parallel across the processor's cores, and after each merge it recounts pairs in the words that contained the merged pair instead of rescanning the whole corpus.

## 4A language model
Given a sequence of tokens, a language model assigns a probability to each token in the vocabulary being the next one. To write text, you sample a token from those probabilities, append it, and ask again. A chat model writes stories and does arithmetic by repeating that step.
stackgrad's model is a decoder-only transformer [6], the architecture behind GPT, Llama, and Qwen, in the modern form taught in Stanford's CS336 [8]. Follow one token through it.
Embedding. The token id selects a row from a learned table, a vector of  d numbers (512 for the story model). Think of the vector as the model's working notes about that position. The notes flow upward through a stack of identical layers, and each layer reads them and adds its own update. That running sum is the residual stream.
Attention is how a position gathers information from earlier positions. Each position computes three vectors from its notes: a query ("what am I looking for?"), a key ("what do I contain?"), and a value ("what do I pass on if chosen?"). The score between two positions is the dot product of one's query with the other's key. Softmax turns the scores into weights that are positive and sum to 1, and the output is the weighted sum of the values: softmax(s)i​=∑j​esj​esi​​,Attention(Q,K,V)=softmax(d ​QK⊤​+M)V
The mask  M holds  −∞ wherever a position would look at a later one, so a position never sees the future it is trying to predict. Dividing by  d ​ keeps the scores from growing with the vector length. A layer runs several of these attention computations side by side, the heads, each with its own weights and so its own pattern. In grouped-query attention [12], several query heads share one set of keys and values, which shrinks the memory they take during generation (§9).
Figure 6 runs the trained story model (§5) on a sentence and draws each head's weights. Most heads spread their weight over several earlier tokens, and their patterns shift from sentence to sentence. A few have a habit you can spot. The figure opens on layer 3, head 11, where words inside a phrase look back to the verb or preposition that introduces it: little, girl, and the first Lily look at was, and red and ball look at with. Position. Attention by itself ignores word order. Shuffle the earlier tokens and the weighted sum stays the same. Rotary position embeddings (RoPE) [10] fix this by rotating each query and key by an angle proportional to its position  p, a different speed for each pair of dimensions. Because rotating both vectors changes their dot product only by the difference of their angles, scores end up depending on how far apart two tokens are: (xi​xi+d/2​​)↦(cospθi​sinpθi​​−sinpθi​cospθi​​)(xi​xi+d/2​​),θi​=b−2i/d
Feed-forward. After attention, each position runs its notes through a small two-layer network on its own. The modern version is SwiGLU [11]: two projections of the input, one passed through a smooth on-off function (SiLU) that acts as a gate on the other, then a projection back down. Normalization before each of these blocks rescales the notes to a steady size, so values neither vanish nor explode across dozens of layers. The RMSNorm [9] version divides by the root mean square and multiplies by learned gains  g: RMSNorm(x)=d1​∑i​xi2​+ϵ ​x​⊙g,FFN(x)=W2​(SiLU(W1​x)⊙W3​x)
In code, a whole layer is two lines (stackgrad/gpt.py):
[CODE]
def forward(self, x, cache=None, pad=None):
    x = x + self.attn(self.attn_norm(x), cache, pad)   # attention, added to the residual stream
    return x + self.ffn(self.ffn_norm(x))              # feed-forward, added the same way
[/CODE]

Output. After the last layer, one more normalization, then a multiplication by a matrix with one row per vocabulary entry, gives a score per token, the logit. Softmax turns the logits into the probabilities we started with. ## 5Can it train a language model?
Training needs a loss, and for next-token prediction the loss is cross-entropy: the negative logarithm of the probability the model gave to the token that came next. Give the right token probability 1 and the loss is 0. Give it 0.25 and the loss is  −ln0.25≈1.39. A model that guesses at random among 10,000 tokens scores  ln10,000≈9.21, and the untrained model's first step scores 9.23, since random weights make near-uniform guesses. The exponential of the loss, the perplexity, is easier to read. A perplexity of 4 means the model is as unsure as a uniform choice among 4 tokens.
The data is TinyStories [7]: millions of short children's stories written by GPT-4 in the vocabulary of a small child. It is small enough to train on one GPU in an hour and simple enough that a small model learns to write coherent stories, which makes progress easy to see. Training repeats one step 40,000 times: take 32 random windows of 256 tokens from the text, compute the loss at every position, run backward, and update every weight.
In code, condensed from train_gpt.py:
[CODE]
for step in range(1, steps + 1):
    opt.lr = cosine_lr(step, max_lr, min_lr, warmup, steps)   # warmup, then cosine decay
    x, y = get_batch(train, batch, context)                   # y is x shifted by one token
    loss = cross_entropy_loss(model(x), y)
    opt.zero_grad()
    loss.backward()
    clip_grad_norm(params, 1.0)
    opt.step()                                                # AdamW
[/CODE]

[ASIDE] The parts of a training step
AdamW [13] [14] is the update rule. Plain gradient descent uses one step size for every weight. Adam keeps a running average of each weight's gradient and of its square, and divides one by the square root of the other, so weights whose gradients stay small still move, and weights with noisy gradients move less. The "W" adds weight decay, which shrinks each weight a little toward zero at each step so weights grow only when the data asks for it.
The learning rate schedule starts small and ramps up over 1,000 steps (warmup), because gradients from random weights are unreliable. It then decays along a cosine curve to 0.0001, so the final steps make fine adjustments instead of large jumps.
Gradient clipping rescales the whole gradient whenever its length exceeds 1, so one unusual batch cannot throw the weights far off course.
Validation scores the model every 500 steps on stories it never trains on. If training loss keeps falling while validation loss rises, the model is memorizing its training stories. [/ASIDE]

The full run used Stanford CS336's configuration: the 22.7M-parameter model of Table 2, 327.7M tokens in all, learning rate 0.001, weight decay 0.1, on one NVIDIA GeForce RTX 3090 through stackgrad's CuPy backend (§6). Figure 7 shows its loss curves.

### Which parts matter
§4 built the model from parts that recent transformers share: RMSNorm before each sublayer, RoPE for position, and SwiGLU in the feed-forward layer. CS336's ablations take each one out and train again. Every variant below trains the story model for 10,000 steps, a quarter of the full run, with everything else unchanged (ablations.json).
The model as built ends at a validation loss of 1.524. Moving RMSNorm after each sublayer, where the original transformer put it, costs 0.013. Replacing SwiGLU with a plain SiLU layer, widened to the same number of parameters, costs 0.03. Dropping position information entirely costs 0.085, the most of the three, yet the model still learns. Haviv et al. [37] found the same and traced it to the causal mask: each position sees a different number of earlier tokens, which tells it roughly where it is.
Without RMSNorm, nothing rescales the vectors between sublayers, and at the full learning rate of 0.001 the run diverged: its loss stopped being a number at step 627, 127 steps after warmup reached the peak rate. At 0.0003 it trains to a validation loss of 1.699, 0.18 behind the model with RMSNorm at its own rate.
One more switch changes the residual itself. TransformerLM(..., attn_res=True) replaces the plain sum of sublayer outputs with Block Attention Residuals: before every sublayer, a learned query takes a softmax over the outputs of earlier layers and mixes them, starting from an equal mix. The story model has not been trained with it here; the Attention Residuals post explains it and measures it on a small model.


## 6Is a GPU faster?
Most of a model's arithmetic repeats one operation over huge arrays, such as multiplying two matrices. A CPU has a handful of fast cores built to run complicated programs one step after another. A GPU has thousands of simple cores that all run the same small program, a kernel, on different pieces of an array at once. That design suits a transformer, which spends its time in large matrix multiplications.
stackgrad runs on three array libraries that share NumPy's interface: NumPy on the CPU as the readable reference, MLX [43] on the Apple laptop's GPU, and CuPy [44] on an NVIDIA GPU. The gradient code in mlops.py never calls any of them by name. Each operation receives a module called xp that exposes the same dozen functions over its own kind of array, so one copy of every gradient runs everywhere, and one call, model.to("metal"), moves a model.
tests/backends.py checks each GPU backend against NumPy. Of 52 gradient checks, 52 agree on the Apple GPU and 51 on the NVIDIA GPU, and the story model, trained on each from the same weights and batches, stays within 4.8e−7 of NumPy's loss (backends_metal.json, backends_cuda.json).

## 7Can a hand-written kernel beat the library's?
Recall attention from §4: compute scores  S=QK⊤/d ​ between every pair of positions, apply the mask, take the softmax, and use the result to average the values. Composed from stackgrad's basic operations, each of those steps is its own kernel. The score matrix has one entry per pair of positions, so for 256 tokens and 16 heads it holds a million numbers per sequence, and every step writes all of them to the GPU's memory and the next step reads them back.
Moving that matrix costs more than computing it. A GPU can do arithmetic far faster than it can move data to and from its memory, so a step that does one multiplication per number it reads spends most of its time waiting for memory. FlashAttention [16] [17] computes attention in one kernel that never writes the score matrix anywhere. It rests on a trick for computing a softmax in a single pass [15].
[ASIDE] Softmax in one pass
A softmax needs the largest score  m (subtracted for numerical safety) and the sum  l=∑j​esj​−m. Both seem to need all scores before you start. But you can keep a running maximum and a running sum, and whenever a larger score arrives, rescale the sum so far by  emold​−mnew​. Take the scores 1, 3, 2. After the first,  m=1 and  l=1. The 3 raises the maximum, so the old sum shrinks to  e1−3=0.135 and the new term adds  e0=1:  l=1.135. The 2 leaves the maximum alone and adds  e−1=0.368:  l=1.503, the same as computing it all at once. The weighted sum of values is rescaled the same way, so one pass over the keys gives the finished output. [/ASIDE]

I wrote three versions as Metal kernels for the Apple GPU (with MLX's mx.fast.metal_kernel), each fixing the previous one's bottleneck:

### Where a training step's time goes
A kernel is worth writing only for an operation that costs something, and a profiler says which ones do. Inside with profile(): (stackgrad/profile.py), every primitive waits for the GPU to finish before the next one starts, so each one's time is its own. One forward and backward pass of the story model on 32 sequences of 256 tokens takes 777 ms this way on the Apple GPU. A normal step, optimizer included, takes 680 ms, because there the GPU queues work without waiting.profile_metal.json lists every primitive.
Matrix multiplications take the most time: 222 ms backward and 94.2 ms forward. Attention comes second, and nearly all of its time is backward: 121 ms, against 8.3 ms for the fused forward, 14.5x. Counting arithmetic predicts 4.4x. The forward makes two matrix products per head, the scores and the weighted sum of values, and skips the 44% of 32-by-32 tiles that the causal mask hides completely. The backward in mlops.py makes five products over every pair of positions: the scores again, then  dV,  dP,  dQ and  dK. It also writes three score-sized matrices,  P,  dP and  dS, to the GPU's memory and reads them back, the traffic the forward kernel exists to avoid. FlashAttention-2 [17] fuses the backward as well.

### The backward as a kernel, in Triton
On the NVIDIA GPU I wrote FlashAttention-2's forward and backward in Triton [34], a Python dialect for GPU kernels in which a program describes the work on one tile and the compiler handles the threads. The forward is the one-pass softmax above. The backward walks the tiles twice: once per block of keys, adding up  dK and  dV, and once per block of queries for  dQ. Each pass rebuilds its tile of  P from the saved log-sum-exp in on-chip memory, so no score-sized matrix reaches the GPU's main memory. Against a 64-bit reference, 5 of 5 checks of the kernels agree to within 1e−4.
At the training shape, forward and backward together take 0.764 ms, against 6.48 ms for the composed version, 8.5x faster (flash_attention_cuda.json lists every shape). In a profiled training step on the NVIDIA GPU, attention's backward takes 3.8% of the time, where on the Apple GPU, with the composed backward, it took 15.6% (profile_cuda.json).


## 8Can it run someone else's model?
Everything so far used a model I trained myself. A stronger test is someone else's model: its published weights should give the same numbers in stackgrad as in the reference library. Qwen3-0.6B [20] is an open chat model from Alibaba's Qwen team, small enough to run on a laptop and capable enough to hold a conversation and work through grade-school math.
Its weights ship as a safetensors file. Eight bytes give the length of a header, the header lists each tensor's name, number type, shape, and byte range as JSON text, and the raw bytes follow. Reading a tensor means slicing out its bytes and reinterpreting them, so loading the file runs no code from it, which is the reason the format exists.
[ASIDE] bfloat16, and why converting it is exact
Qwen ships its weights in bfloat16, a 16-bit number format. A standard 32-bit float spends 1 bit on the sign, 8 on the exponent (the scale), and 23 on the mantissa (the digits). bfloat16 keeps the same sign and exponent and the first 7 mantissa bits. It covers the same range of sizes with two to three significant digits instead of seven, in half the memory. Because bfloat16 is the first half of a 32-bit float, stackgrad converts it by appending 16 zero bits, and the conversion loses nothing. [/ASIDE]

Qwen3 is the model of §4 with four settings changed (Table 2). Each head is 128 numbers wide, set apart from the model's width. Qwen3 normalizes queries and keys before RoPE, which keeps attention scores in a steady range. The normalization constant is smaller. And the output layer reuses the embedding table instead of a separate matrix, which saves 156M parameters. The loader maps each of Hugging Face's tensor names to a stackgrad parameter and refuses to run if any name or shape fails to match, because a weight that keeps its random starting value without warning produces a model that runs and talks nonsense.

## 9Can it serve two people at once?
stackgrad now computes the same scores as the reference, one forward pass at a time. A chat reply needs one forward pass per new token, hundreds in all. Without care, step  t recomputes the keys and values of all  t earlier tokens, although they never change. The KV cache stores them instead: each step computes keys and values for the one new token, appends them, and attends over the stored ones. The work per token stops growing with the length of the text. The price is memory, since each token of each conversation keeps its keys and values for each layer.
That memory limits how many people one GPU can serve. Reserving the maximum length for each request wastes the part a short reply never uses. vLLM's PagedAttention [18] stores the cache in small fixed-size blocks, handed out as a sequence grows and taken back the moment it finishes. stackgrad's block manager keeps the same books: it counts each sequence's blocks and decides which requests run. The memory itself stays one array per cache.
The second idea is continuous batching [19]. A plain batch of requests runs until its longest reply finishes, while finished requests sit idle. stackgrad's scheduler instead admits new requests between any two generation steps, runs every admitted request through each step together, and lets each one leave as soon as it is done. If the cache runs out of blocks, the scheduler preempts the newest request. That request gives back its blocks, waits, and later rebuilds its cache from its prompt plus the tokens it had already produced.
Running several conversations through one step needs their caches to line up, and each conversation's cache has its own length. The runner pads each cache on the left to the longest and masks the padding out of attention. Each new token keeps the position it holds in its own conversation, so RoPE sees the distances it would see alone. While the same requests keep running, the padded caches stay together and grow by one position per step. When a request joins or leaves, the runner splits them apart and pads the new set, copying every cache; an attention kernel that read each sequence's keys and values through its own list of blocks would skip the copy. The padding also takes memory the block manager never counts: a short conversation beside a long one holds as many positions as the long one.
tests/serve.py checks the scheduler with greedy decoding, where each request must receive the same tokens it gets when it runs alone. Under each of 3 loads every request does, including a run with 3 preemptions when the whole cache holds only 9 blocks (serve_cpu.json).

## 10Can decoding go faster?
Each reply in Figure 12 streams at the pace of the decode step. Generating one token runs the whole model once and reads each weight from memory once. For a 0.6B-parameter model in bfloat16 that is about 1.2 GB per token. The arithmetic is cheap by comparison, so memory bandwidth sets the speed of generation. No implementation can produce tokens faster than the bandwidth divided by the bytes of weights. There are two ways past that limit: read fewer bytes per token, or get more than one token from each read.
Quantization reads fewer bytes. stackgrad cuts each row of a weight matrix into groups of 64, keeps a scale and an offset per group, and rounds every weight to one of  2bits levels; its own Metal kernel multiplies against the packed integers and matches MLX's on the same bytes (tests/quant.py). Four bits cut the weights read per token from 1,192 MB to 335 MB, for 19.3% higher perplexity on math text. Yet a decode step goes only from 24.7 ms to 20.9 ms. Reading the bfloat16 weights takes 11.9 ms of the step at the measured bandwidth; the rest is hundreds of small operations, each paying a kernel launch (§6), and quantizing leaves those as they were (quant.json).
Speculative decoding [21] [22] gets more than one token from each pass instead. A small draft model guesses the next few tokens, the large model checks all of them in one pass, and it keeps the guesses it agrees with by a rule that leaves its output distributed exactly as before (tests/speculative.py). With Qwen3-0.6B drafting for Qwen3-1.7B, the target kept 80% of single guesses and every output matched the 1.7B's own text token for token, yet the best speedup was 1.07x, at 1 guess per pass (speculative_metal.json). The draft costs too much: a 0.6B decode step takes 61% of a 1.7B step, because both models have 28 layers, launch the same number of kernels, and pay §6's launch cost for each.


## 11Does fine-tuning make it better at math?
A pretrained model knows a great deal but has its own habits. Fine-tuning trains it a little further on examples of the behaviour you want. Full fine-tuning updates every weight, and Adam stores two extra numbers per weight, so even a 0.6B model needs memory for several copies of itself.
LoRA [23] (low-rank adaptation) freezes the original weights and learns a small correction next to each weight matrix. A matrix  W with  nin​ inputs and  nout​ outputs gets a correction  AB, where  A has  r columns and  B has  r rows for a small rank  r: y=xW+rα​(xA)B,frozen   nin​⋅nout​​​≫trained   r(nin​+nout​)​​
 B starts at zero, so training starts from the original model unchanged. For a 1024 by 1024 matrix at rank 16, the correction has 32,768 numbers against the matrix's 1,048,576. Across all seven matrices of all 28 layers, Qwen3-0.6B gets 10,092,544 trainable numbers, 1.69% of the model. After training,  AB is added into  W once, and the fine-tuned model runs at the original's speed.
The task is GSM8K [24]: grade-school math word problems that take a few steps of arithmetic, each with a worked solution ending in #### answer. The model trains on the 7,473 training problems, learning to produce the solutions while the loss ignores the question. I fixed the evaluation protocol before training: the first 250 test problems, the same prompt asking for the answer after ####, greedy decoding with thinking mode off, and at most 320 new tokens. A problem counts as solved when its final number, the first #### or \boxed{} answer, equals the reference (bench/gsm8k.py says why the first).
This run kept every activation for backward and fit 2 examples per pass. Activation checkpointing [36], which keeps only each block's input and recomputes the rest during backward, fits all 8 in 5.23 GB on the 3090 (checkpointing_cuda.json).

## 12Does learning from its own answers help?
LoRA in §11 trained the model to copy solutions, and it got worse at what Table 5 counts. Reinforcement learning trains on that count. The model writes its own replies, a checker scores each one, and training makes the replies that scored well more likely. The checker here is the evaluation's rule: a reply earns 1 if its final number equals the reference and 0 otherwise. Nothing tells the model how to reason, only whether its answer came out right.
The update comes from the policy gradient [25]. Write  πθ​(o∣q) for the probability that the model, with weights  θ, answers question  q with reply  o, and  R(o) for the reply's score. The gradient of the expected score is an expectation too, so sampled replies estimate it: ∇θ​Eo∼πθ​​[R(o)]=Eo∼πθ​​[R(o)∇θ​logπθ​(o∣q)]
Stepping along  R(o)∇θ​logπθ​(o∣q) makes scoring replies likelier. Used raw, it pushes up every correct reply by the same amount, even on a question the model never gets wrong, and the estimate is noisy. GRPO [26] (group relative policy optimization) samples a group of replies to each question and scores each reply against its siblings: Ai​=stdj​R(oj​)+ϵR(oi​)−meanj​R(oj​)​,L=−N1​i=1∑N​Ai​B1​t∑​logπθ​(oi,t​∣q,oi,<t​)
A reply better than its group's average gets a positive advantage  Ai​ and becomes likelier, and a worse one becomes less likely. A group whose replies all scored the same, all right or all wrong, says nothing about which reply was better: every advantage in it is zero, and stackgrad skips those replies in the update. A reply's log-probabilities are summed and divided by  B, the same 320-token budget for every reply, not by the reply's own length, which would give a long wrong reply a smaller push per token than a short one (Liu et al. [27]).
In code the loss is a weighted sum of the replies' token log-probabilities, condensed from policy_loss in train_grpo.py:
[CODE]
logp = log_softmax(logits, axis=-1)[rows, targets]                  # each reply token's log-probability
weight = np.repeat(advantages / budget / n_replies, reply_lengths)  # A_i / (B N), once per token
loss = -(logp * weight).sum()
[/CODE]

[ASIDE] Four replies to one question
Say one reply of four is right: scores 1, 0, 0, 0. The mean is 0.25 and the standard deviation 0.433, so the right reply's advantage is  (1−0.25)/0.433=1.73 and each wrong reply's is  (0−0.25)/0.433=−0.58. The right reply gets pushed up three times as hard as each wrong one gets pushed down, and the pushes cancel:  1.73=3×0.58. [/ASIDE]

Training starts from the released Qwen3-0.6B, not the LoRA model of §11, with a fresh LoRA adapter of the same size. Its learning rate, 0.0001, is ten times CS336's rate for training every weight, the ratio "LoRA Without Regret" [28] recommends. Each step samples 8 replies to each of 8 training problems at temperature 1 and makes one update.
Sampling takes most of each step, up to 320 decode steps of one token each, and a decode step for one reply leaves most of the GPU idle (§6). Sampling all 64 replies in one batch fills it. On the 3090 a decode step takes 79 ms for one reply and 86.4 ms for 64, so the batch writes 58 times as many tokens per second (rollout_cuda.json). Prompts of different lengths share the batch by padding on the left, with the padding masked out of attention (tests/grpo.py). The first version still crawled. It copied all 64 rows of logits, 151,936 numbers each, to the CPU to draw the tokens, which took 98.5 ms per step against the model's 84.3 ms; drawing them on the GPU takes 1.2 ms.

### The reward the model gamed
The first run used the reward above, the final number alone. From step 51 on, every reply it sampled ran to the 320-token limit (Figure 14). The model had found replies the reward could not tell from good ones: it wrote its solution, then "The final answer is  18​." between rows of dashes, over and over, until the limit cut it off. The number stayed right, and nothing in the reward cost the model anything for writing on. On the test problems that adapter solves 154 of 250, against 152 before training, and all 250 of its replies hit the limit (Table 6).
The fix makes stopping part of the answer. A reply earns 1 only if it ends with Qwen's end-of-turn token and its final number is right, so a reply the limit cuts off scores 0 whatever it says.

## 13Can it answer from documents and use a tool?
Most systems built on language models do one of two things: answer from documents the model looks up, or let it call tools. Here both run on stackgrad end to end. They are programs that talk to the server of §9 through its chat endpoint, the way an application uses any hosted model, and stackgrad computes every number between the question and the answer, from the embedding to the last sampled token.

### Retrieval
A small model knows few facts. Retrieval-augmented generation [39] looks up passages that bear on a question and puts them in the prompt. The test is SQuAD v1.1 [40]: questions people wrote about Wikipedia paragraphs, with the answers they marked in the text. Its development set has 2,067 paragraphs.
Finding the right paragraph needs a way to compare meanings. An embedding model maps a text to a vector so that texts about the same thing point the same way. Qwen3-Embedding-0.6B [41] has Qwen3's architecture with its own weights, so stackgrad runs it with the code of §8, and its embedding of a text is the final hidden state of the last token, scaled to length 1. The index is a NumPy matrix with one row per paragraph, built once in 363 s on the Apple GPU. Embedding a question takes 61 ms, and the search is one matrix product with the index and a sort: the largest dot products are the nearest paragraphs.
[CODE]
query = embed(model, tok, [INSTRUCT + question], device)[0]   # 1,024 numbers, length 1
scores = index @ query                                          # one dot product per paragraph
top = np.argsort(-scores)[:3]                                   # the three nearest
[/CODE]

For 200 questions drawn at random, the paragraph the question was written from ranks first 73.0% of the time and among the top 3 paragraphs 91.5% of the time. The server then answers each question with the top 3 paragraphs in its prompt.
SQuAD scores an answer by exact match and by word overlap (F1), after lowercasing and dropping punctuation and articles. Qwen3 answers in sentences, such as "The chloroplast double membrane is sometimes compared to the mitochondrial double membrane.", which is right and scores 0 on exact match. Table 7 therefore also counts whether an answer contains a reference answer as whole words: 55% do. Asked without the paragraphs, the same questions set a floor, since SQuAD's questions presuppose their paragraph ("the event that compelled the protection of German private schools"): closed-book, only 3% of answers contain the reference. The paragraphs cost time, since the prompt grows by three of them: an answer takes 1.53 s against 0.48 s. Figure 16 runs the whole pipeline on a question of your own.

### A calculator
GSM8K's problems take a few steps of arithmetic, and a 0.6B model slips on arithmetic. Qwen3 was trained to call tools: shown a function's description in its system prompt, it can stop in the middle of a reply and write a call as JSON between <tool_call> tags. apps/agent.py gives it a calculator and runs the loop ReAct [42] describes: when a reply calls the tool, the program evaluates the expression and sends the value back as a tool message, and the model continues, until it answers without a call. The expression comes from the model, so the calculator parses it and evaluates numbers and arithmetic only, and never runs it as code (tests/agent.py). stackgrad writes tools and tool results into the prompt exactly as Hugging Face's chat template does, which tests/tokenizer.py checks token for token.
The first run kept §11's prompt, which says "Solve it step by step", and offered the calculator in the system message. In 250 problems the model never called it, and Hugging Face's Qwen3-0.6B ignores it the same way on that prompt. The offer still changed the answers. Replies shrank from 213 tokens on average to 148, and the model solved 132 problems against 152: it fixed 21 and broke 41, a split that chance produces 1.5% of the time. Told to solve step by step, it does, whatever the system message says. The second run asks for the calculator in the user's turn instead.
Asked in the user's turn, the model called the calculator 440 times, on 248 of 250 problems, and solved 42 against 152 without it: it fixed 7 problems and broke 117, a split that chance produces less than 0.01% of the time. A problem took 2 calls to the model on average, and a reply averaged 27 tokens, little more than the calls themselves. The model handed the calculator its arithmetic before working out what to compute, then answered with the number that came back (bench/results/gsm8k_agent_replies.jsonl has every trace). ### Scaling laws (CS336 assignment 3)
Was the story model of §5 the right size for its compute? Training costs about six floating-point operations per parameter per token: a multiply and an add in the forward pass, and twice that in the backward. The full run spent  3.5×1016 of them. The same compute could buy a larger model trained on fewer tokens, or a smaller one on more. Hoffmann et al. [38] find the best split with IsoFLOP curves: fix a budget  C, train models of several sizes  N, counting only the weights in matrix products (the embedding table is a lookup and multiplies nothing, so the story model counts as 17.6M), each on  C/6N tokens, and see which ends lowest. I ran three budgets, from  3×1014 to  3×1015 operations, with five sizes each (Figure A1).
[CAPTION] Figure A1: IsoFLOP curves from scripts/scaling.py: the final validation loss of TinyStories models of five sizes, each trained on exactly its budget's tokens. Darker lines spend more compute. A ring marks the bottom of the parabola fitted to each curve.
Each curve has a bottom. A model too small cannot hold what the data teaches, and one too large sees too few tokens to fit its weights. A parabola through each curve, in the logarithm of the size, puts the best size at 3M, 5.5M, and 8.2M parameters, which grows as  C0.43. That exponent is loose. The smallest budget's losses only rise from its smallest model on, so its bottom sits at the edge of the grid and its value leans on the parabola; the two larger budgets alone give  C0.37.
Carried 12 times past the largest budget, to the full run's compute, the fit asks for 24M parameters on 237M tokens, or 20M with the two-budget exponent. The run used 17.6M on 328M: a model 1.1 to 1.4 times smaller than the fit's choice, and so, at the same compute, trained on that many times more tokens.
